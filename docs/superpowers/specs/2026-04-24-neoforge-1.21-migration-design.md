# AttributesLib NeoForge 1.21 Migration Design

## Goal

Port AttributesLib from the current Forge 1.20.1 codebase to a NeoForge 1.21 codebase while preserving the public mod identity, package namespace, API intent, and gameplay behavior. The migration should be staged, but migrated pieces must be implemented in their intended final shape rather than as temporary compile-only stubs.

## Source Inputs

- Base codebase: `/home/hhoa/git/hhoa/AttributesLib1`
- Reference template: `/home/hhoa/git/hhoa/examplemod-template-1.21`
- Target worktree: `/home/hhoa/git/hhoa/AttributesLib1/.worktrees/neoforge-1.21`
- Target branch: `neoforge-1.21`

## Constraints

- Preserve `mod_id=attributeslib`.
- Preserve the base Java package `dev.shadowsoffire.attributeslib` unless a specific 1.21 platform change requires otherwise.
- Use NeoForge 1.21 and Java 21.
- Prefer NeoForge public APIs over migrated ASM, coremod, or mixin hooks when an equivalent public hook exists.
- Keep client-only code isolated from common and dedicated-server load paths.
- Do not introduce placeholder behavior to make a stage compile. If a feature cannot be ported yet, leave it out of that stage and document the reason.
- Do not include the untracked `examplemod-template-1.21/` directory from the original `AttributesLib1` main worktree in migration commits.

## Architecture

The NeoForge 1.21 version should keep the existing domain-oriented package layout:

- `AttributesLib`: mod entrypoint. It wires the mod event bus, common event bus, config, network, and client entrypoints.
- `api`: public events, objects, formatting helpers, and integration surface for dependent mods.
- `impl`: server-safe gameplay implementation, including attribute application, combat math, damage hooks, healing hooks, and entity events.
- `client`: client event handlers, GUI screens, tooltip behavior, and rendering support.
- `packet`: network payload definitions and registration.
- `mobfx`: custom mob effects.
- `util`: shared helpers with no platform lifecycle responsibilities.
- `mixin` and `asm`: retained only where NeoForge 1.21 lacks a suitable public hook.

The build should be based on the NeoForge template style:

- `net.neoforged.moddev`
- Java 21 toolchain
- `src/main/templates/META-INF/neoforge.mods.toml`
- explicit resources and mixin configuration
- NeoForge run definitions for client, server, game test server, and data generation

The legacy build-time generation for `mixins.json` and `coremods.json` should not be carried forward as-is. It is path-sensitive and was observed to produce malformed lookup paths inside a `.worktrees/neoforge-1.21` directory because it applies dot replacement to the whole project path. The 1.21 build should use explicit, stable metadata.

## Migration Phases

### Phase 1: Platform Skeleton

Replace the ForgeGradle build with the NeoForge 1.21 template structure while preserving the project identity. This phase owns Gradle files, wrapper compatibility, metadata templates, pack metadata, and the minimal mod entrypoint wiring needed for NeoForge to discover the mod.

Acceptance:

- Gradle can configure the project.
- Java toolchain targets 21.
- `attributeslib` metadata is generated from template inputs.
- The mod entrypoint uses NeoForge constructor injection with `IEventBus` and `ModContainer`.

### Phase 2: Registration And Entrypoints

Replace Forge registration helpers with NeoForge `DeferredRegister` usage or a local helper that wraps NeoForge primitives without preserving Forge-only dependencies. Register attributes, mob effects, sounds, and serializers in a stable, explicit order.

Acceptance:

- Registered objects use NeoForge registry holders.
- The main mod class no longer depends on `FMLJavaModLoadingContext`, `MinecraftForge` Forge packages, or Forge `RegistryObject`.
- Client registration is isolated behind a client-only entrypoint.

### Phase 3: Core Gameplay

Port server-safe events and gameplay behavior: attribute attachment, combat attributes, protection and armor modifiers, life steal, crits, dodge, projectile behavior, healing, experience modifiers, and effect behavior.

Acceptance:

- Core events compile against NeoForge 1.21 event classes.
- Behavior intent matches Forge 1.20.1 where the underlying Minecraft mechanics still exist.
- Any behavior that relies on removed hooks is either implemented through a 1.21 replacement or documented for the mixin phase.

### Phase 4: Config And Networking

Move configuration to NeoForge-native config where practical. Port `CritParticleMessage` and any other packets to the NeoForge 1.21 networking model.

Acceptance:

- Config values load through the NeoForge lifecycle.
- Packets are registered through NeoForge payload registration.
- Packet handlers keep side-specific work on the correct thread and distribution side.

### Phase 5: Client UI And Tooltips

Port the attributes screen, tooltip formatting, potion/effect tooltip hooks, and client event handling.

Acceptance:

- Dedicated server compile and runtime paths do not load client classes.
- Attribute GUI and tooltip behavior match the original intent.
- Client event handlers use NeoForge 1.21 event names and signatures.

### Phase 6: Mixin And Hook Audit

Review each existing mixin, ASM hook, access transformer, and coremod script. Prefer removal or replacement with public NeoForge APIs. Keep invasive hooks only when they remain necessary for behavior parity.

Acceptance:

- Mixin config is explicit and valid.
- No legacy coremod JSON generation remains.
- Access transformers are retained only for still-needed targets.
- Final `build` passes with the full migrated feature set.

## Verification Strategy

Run verification at the end of each meaningful slice:

- `./gradlew compileJava`
- `./gradlew processResources`
- `./gradlew build`

Use narrower commands while actively porting a failing area, but do not call the migration complete until the full build passes. When a phase intentionally leaves a later feature unported, record it in the implementation notes rather than hiding it behind placeholder code.
